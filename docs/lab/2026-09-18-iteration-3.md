## Implemented: seat-aware Party Needs

The first PartyNeeds prototype could overstate DPS demand in malformed or transitional compositions. Example: two tanks + two DPS leaves one physical party seat; because a healer is still missing, advertising another DPS seat is not actionable. A full group missing Lust could also make `WouldAddCoverage` report that an applicant adds Lust even though there is no seat.

Iteration 3 hardens the pure engine:

- adds `slotsOpen` and `unknownRoles` diagnostics;
- reserves remaining physical seats for missing tank/healer before calculating DPS demand;
- caps DPS demand by actual remaining seats;
- makes applicant coverage fail closed when the party is full;
- keeps utility coverage factual even in an invalid/full composition, without turning it into an invite recommendation;
- preserves language-neutral engine tokens, so no visible localization keys were added.

Tests now cover duplicate-role seat pressure, full-party applicant rejection, unknown-role diagnostics and revised seat-aware token output.

## Safety / product decision

No protected action was added. No automatic invite, decline, sort, apply, countdown or keystone activation is performed. No OnUpdate loop was introduced. This iteration intentionally improves correctness before adding more Blizzard UI surface area.

## Validation limitation

The automation container has no Lua/LuaJIT interpreter and cannot clone GitHub over its network, so the repository's executable Lua suite cannot be run in this environment. Tests were updated but are not claimed as passing. Final packaging must execute the normal suite in an environment with the repository test runtime before acceptance.
