# Experimental M+ Lab — Iteration 4

Branch only: `experiment/mplus-lab-2026-09-18`. Stable/main/develop remain untouched.

## Fresh evidence checked

Public community evidence checked on 2026-09-18 continues to converge on the same Group Finder problem: leaders get very large DPS queues and explicitly choose for missing group utility such as Bloodlust and battle resurrection; users of current LFG replacements request visible Lust/BRez information, specs, clearer composition context, and less scanning. OAK LFG Sorter v2.0 feedback is especially useful because it also exposes the danger of replacing too much Blizzard UI at once (window-sync/conflict reports).

A separate 2026 community thread around M+ pace HUDs reinforces a second product principle: useful M+ enhancements should answer one immediate question with low visual noise instead of duplicating the entire Blizzard tracker. That remains relevant to the later Blizzard UI Enhancer work, but this iteration stays focused on LFG.

## Public source/API inspection

Inspected current public `Smokenoaken/OakLFGSorter` source only for API shape, not implementation. The repository is not treated as reusable source. Its current code reads `C_LFGList.GetApplicantMemberInfo(applicantID, memberIndex)` for class, role flags, score and spec context. This confirms a current read-only path for applicant data without automating invite/decline actions.

## Implemented: applicant coverage model

Extended `LFGCompositionHint` with a deliberately read-only applicant coverage layer:

- `ReadApplicantMember()` reads one applicant member defensively with `pcall` and normalizes only class/role/spec context needed by Mitzu.
- `BuildApplicantCoverage()` asks the existing pure `PartyNeeds:WouldAddCoverage()` engine what factual gaps that applicant would cover.
- `GetApplicantCoverageText()` composes the current party snapshot with the applicant model.
- Output is intentionally descriptive (`Covers: DPS seat - Bloodlust`) rather than a score, ranking, invite recommendation or filter.
- Added applicant-list update events so the experimental model can refresh without polling or an `OnUpdate` loop.

This is groundwork for a future tiny row/tooltip affordance. This iteration does **not** hook or replace Blizzard applicant rows yet; that surface is deferred until Retail frame behavior can be validated to avoid taint, layout conflicts and duplicate information with Raider.IO.

## Localization

Added six new visible concepts through the isolated `MitzuMPlusExperimental` AceLocale namespace. English remains the base/default locale and Spanish has exact key parity. No new visible string is hardcoded in the UI module.

## Tests

Expanded `LFGCompositionHint.spec.lua` to cover:

- localized applicant coverage for Bloodlust and battle resurrection;
- no recommendation when the party has no open seat;
- exact enUS/esES parity, now 13 experimental keys.

The automation environment still has no Lua/LuaJIT runtime, so executable Lua tests are not claimed as passing here. The final build must run the repository's normal Lua/static suite before packaging.

## Safety decision

No invite, decline, sort, filter, application, ready check, countdown, keystone activation, protected-frame write, or continuous polling was added. The implementation remains read-only and fail-closed when APIs are absent.
